# 项目配置文件 pyproject.toml

最新开发项目推荐使用pyproject.toml，可以复用python现代项目中的[build-system]声明构建后端机器依赖,[project]定义项目元数据、依赖等。

单独定义[tool.pytest.*],对pytest可以单独配置：

```ini
[project.entry-points.pytest11]
my-plugin-name = "my_plugin_module.plugin"

[tool.pytest.ini_options]
minversion = "7.0"
addopts = "-ra -q --strict-markers"
testpaths = ["tests"]
markers = [
    "slow: marks tests as slow",
    "integration: integration tests",
]
```

# conftest.py插件注册

## pytest定义的整体生命周期

pytest 启动后大致经历：

```text
启动配置
  ↓
收集阶段（Collection）
  ↓
运行阶段（Run）
  ↓
报告与退出
```

其中，`conftest.py` 里的不同 hook 分布在不同的阶段：

| 阶段 | 典型 hook / 行为 |
| :--- | :--- |
| 启动配置 | `pytest_addoption`、`pytest_configure` |
| **收集阶段** | `pytest_collect_file`、`pytest_generate_tests`、`pytest_collection_modifyitems` |
| **运行阶段** | `pytest_runtest_setup`、`pytest_runtest_call`、`pytest_runtest_teardown`、`pytest_runtest_makereport` |
| 结束 | `pytest_unconfigure`、`pytest_sessionfinish` |

---

## 收集阶段（Collection）

收集阶段的任务是：**找出所有测试，并生成测试项（test items）**。

具体包括：

1. 从命令行指定的路径（或 `testpaths`）开始扫描。
2. 根据命名规则识别测试文件、测试类、测试函数。
3. 解析 `@pytest.mark.parametrize`，为每组参数生成一个测试项。
4. 执行 `pytest_generate_tests`，动态生成参数化。
5. 执行 `pytest_collection_modifyitems`，对测试项进行过滤、排序、加 marker。
6. 最终产出一个 `items` 列表，每个 `item` 代表一个即将运行的测试。


### 常见 hook

```python
def pytest_collection_modifyitems(config, items):
    """收集完成后，对 items 做最后调整。"""
    # items 是收集到的所有测试项
    for item in items:
        if "slow" in item.keywords:
            item.add_marker(pytest.mark.skip(reason="slow test"))
```

```python
def pytest_generate_tests(metafunc):
    """为测试动态生成参数。"""
    if "env" in metafunc.fixturenames:
        metafunc.parametrize("env", ["dev", "staging", "prod"])
```

### 如何观察收集阶段

```bash
pytest --collect-only -q
```

只收集、不运行，输出所有测试项：

```text
tests/test_api.py::test_login[dev]
tests/test_api.py::test_login[staging]
tests/test_api.py::test_login[prod]
```


## 运行阶段（Run / Execution）

运行阶段的任务是：**逐个执行收集阶段生成的测试项**。

每个测试项的执行又分为三个子阶段：

```text
setup    → 准备（fixture 初始化）
call     → 执行测试函数
teardown → 清理（fixture 清理）
```

对应 pytest 的 hook：

| 子阶段 | hook | 说明 |
| :--- | :--- | :--- |
| setup | `pytest_runtest_setup` | 测试函数执行前，初始化 fixture |
| call | `pytest_runtest_call` | 真正执行测试函数 |
| teardown | `pytest_runtest_teardown` | 测试结束后，清理 fixture |
| 报告 | `pytest_runtest_makereport` | 生成测试结果报告 |

fixture 在运行阶段才真正实例化：

- `yield` 之前的 setup 在 `setup` 子阶段执行。
- `yield` 之后的 teardown 在 `teardown` 子阶段执行。

### 作用域与运行阶段

fixture 的 `scope` 决定了它在运行阶段的哪个层级初始化：

| scope | setup 时机 | teardown 时机 |
| :--- | :--- | :--- |
| `function` | 每个测试项 setup 时 | 每个测试项 teardown 时 |
| `class` | 每个测试类第一个测试 setup 前 | 该类最后一个测试 teardown 后 |
| `module` | 每个测试文件第一个测试 setup 前 | 该文件最后一个测试 teardown 后 |
| `session` | 整个运行阶段开始时 | 整个运行阶段结束时 |

精细限定fixture的scope在module可以在不同的测试目录层级下创建conftest.py，在其中定义fixture

### conftest.py 中的执行顺序

```python
def pytest_configure(config):
    # 启动配置阶段，最早执行
    ...

def pytest_collection_modifyitems(config, items):
    # 收集阶段，fixture 还没实例化
    ...

@pytest.fixture
def client():
    # 运行阶段，每个测试 setup 时才执行
    ...

```

# 交叉能力分析

`[tool.pytest.ini_options]` 是**声明式静态配置**，`conftest.py` 是**命令式编程接口**。
两者提供的能力有重叠

## 重叠的能力

| 功能 | `pyproject.toml` 配置 | `conftest.py` 等价写法 |
| :--- | :--- | :--- |
| **注册 marker** | `markers = ["slow: ..."]` | `config.addinivalue_line("markers", "slow: ...")` |
| **过滤警告** | `filterwarnings = ["error"]` | `warnings.filterwarnings("error")` |
| **添加默认参数** | `addopts = "-ra -q"` | `config.option.verbose = 1` 等逐项设置 |
| **忽略测试路径** | `norecursedirs = [...]` | `collect_ignore` / `collect_ignore_glob` |
| **设置测试路径** | `testpaths = ["tests"]` | `pytest_collection_modifyitems` 里过滤 |
| **加载插件** | `addopts = "-p myplugin"` | `pytest_plugins = ["myplugin"]` |
| **修改日志行为** | `log_cli`, `log_level` | `pytest_configure` 里操作 `logging` |
| **设置 pythonpath** | `pythonpath = ["src"]` | `sys.path.insert(0, "src")` |

### 只有 `conftest.py` 支持的能力

| 能力 | 说明 |
| :--- | :--- |
| **定义 fixture** | ini 里根本没有 fixture 的概念 |
| **实现 hook** | `pytest_collection_modifyitems`、`pytest_runtest_setup` 等 |
| **添加命令行选项** | `pytest_addoption` |
| **动态条件逻辑** | 根据环境变量、CI 状态、Python 版本分支 |
| **按目录层级覆盖** | 子目录的 `conftest.py` 可以覆盖父级的 fixture/hook |
| **访问运行时对象** | `request`、`config`、`item`、`session` 等 |

### 只有 `pyproject.toml` 支持的能力

| 能力 | 说明 |
| :--- | :--- |
| **声明项目级元数据** | `minversion`、`required_plugins` |
| **静态路径配置** | `testpaths`、`norecursedirs` |
| **声明式 warning 过滤** | 比代码更直观 |
| **插件默认启用/禁用** | `-p no:cacheprovider` 等 |
| **CI 无关的统一配置** | 不依赖代码执行 |

---

## 关键差异：**声明式 vs 命令式**

| 维度 | `[tool.pytest.ini_options]` | `conftest.py` |
| :--- | :--- | :--- |
| **性质** | 静态配置，声明式 | 代码，命令式 |
| **何时生效** | pytest 启动时读取 | 收集/运行时执行 |
| **可调试性** | 看得见，改起来直观 | 需要读代码 |
| **动态能力** | 无（除了环境变量插值） | 完全动态 |
| **作用域** | 整个项目 | 按目录层级作用 |
| **可复用性** | 复制配置 | 可以打包成插件 |
| **能否条件分支** | 不能 | 可以 |


## 该怎么选：实用原则

### 优先用 `pyproject.toml` 的情况

- 配置是**静态的、项目级的**，不依赖运行时状态
- 例如：`markers`、`testpaths`、`addopts`、`filterwarnings`、`log_cli`
- 理由：可见性高、不执行代码、易于审查

### 必须用 `conftest.py` 的情况

- 需要**根据环境/条件动态变化**
- 需要**定义 fixture**
- 需要**实现 hook**
- 需要**按目录层级覆盖初始化动作**
- 需要**访问 pytest 运行时对象**

### 两者都用但要注意优先级的情况

当同一功能两边都配置时，行为通常是**叠加**而非覆盖：

```toml
# pyproject.toml
markers = ["slow: ..."]
```

```python
# conftest.py
def pytest_configure(config):
    config.addinivalue_line("markers", "integration: ...")
```

结果：两个 marker 都被注册，**不冲突**。

但如果是 `filterwarnings`，两边都设置，顺序会影响最终行为——**后应用的规则优先**，而 conftest 的 `pytest_configure` 在 ini 之后执行，所以 conftest 里的规则会覆盖 ini 中冲突的规则。


## 总结

| 问题 | 答案 |
| :--- | :--- |
| 是否有重叠？ | **有**，约 8 类配置项功能重叠 |
| 重叠时用哪个？ | 静态配置优先用 ini；动态/条件/层级覆盖用 conftest |
| 能否完全互相替代？ | **不能**。fixture、hook、`pytest_addoption` 只能写在 conftest |
| 会互相冲突吗？ | 大多数情况是**叠加**；`filterwarnings` 等顺序敏感项，conftest 后执行会覆盖 ini |

# parameter数据驱动应用
你说的 “parameter” 在 pytest 里通常指**参数化**，核心是 `@pytest.mark.parametrize`。用好它的关键是：**选对入口、控制组合爆炸、写好 ID、和 fixture 配合、动态场景用 hook**。

---

## 一、三种参数化入口，先分清

| 方式 | 用在哪 | 适合场景 |
| :--- | :--- | :--- |
| `@pytest.mark.parametrize` | 测试函数/测试类 | 一个测试逻辑，多组输入输出 |
| `@pytest.fixture(params=...)` | fixture | 多个测试共享同一组参数化资源 |
| `pytest_generate_tests` | hook，插件常用 | 动态生成参数，如从 JSON/YAML/DB 读用例 |

---

## 二、`@pytest.mark.parametrize` 基础与进阶

### 1. 基本写法

```python
import pytest

@pytest.mark.parametrize("x, y, expected", [
    (1, 2, 3),
    (0, 0, 0),
    (-1, 1, 0),
])
def test_add(x, y, expected):
    assert x + y == expected
```

### 2. 多组参数叠加：笛卡尔积

```python
@pytest.mark.parametrize("x", [0, 1])
@pytest.mark.parametrize("y", [2, 3])
def test_mul(x, y):
    assert x * y >= 0
# 生成 2 × 2 = 4 个测试
```

**注意**：叠加是笛卡尔积，容易爆炸，用之前先算数量。

### 3. 给参数起可读 ID

```python
@pytest.mark.parametrize(
    "env",
    ["dev", "staging", "prod"],
    ids=["development", "staging", "production"],
)
def test_env(env):
    ...
```

测试名会变成 `test_env[development]`，`-k` 过滤更方便：

```bash
pytest -k "production"
```

### 4. 用 `pytest.param` 精细控制单个用例

```python
@pytest.mark.parametrize("value, expected", [
    pytest.param(1, 1, id="positive"),
    pytest.param(0, 0, id="zero"),
    pytest.param(-1, 1, id="negative", marks=pytest.mark.slow),
    pytest.param(999, 0, id="bug", marks=pytest.mark.xfail(reason="known bug")),
])
def test_abs(value, expected):
    assert abs(value) == expected
```

`pytest.param` 可以挂：
- `id`：用例 ID
- `marks`：marker，如 `skip`、`xfail`、`slow`

### 5. 间接参数化 `indirect`

参数不直接传给测试，而是传给同名 fixture：

```python
@pytest.fixture
def user(request):
    return {"name": request.param, "id": hash(request.param)}

@pytest.mark.parametrize("user", ["alice", "bob"], indirect=True)
def test_user(user):
    assert user["name"] in ["alice", "bob"]
```

也可以只让部分参数走 indirect：

```python
@pytest.mark.parametrize("x, y", [(1, 2)], indirect=["x"])
def test_partial(x, y):
    ...
```

## 三、fixture 参数化

适合“多个测试共享同一组参数化资源”：

```python
@pytest.fixture(params=["dev", "staging", "prod"], ids=["dev", "stg", "prod"])
def env(request):
    return request.param

def test_api(env):
    assert call_api(env) == 200

def test_db(env):
    assert connect_db(env) is not None
# 每个依赖 env 的测试都自动跑 3 次
```

**要点**：
- `request.param` 拿到当前参数值。
- 可以配合 `pytest.skip` 动态跳过某些参数：

```python
@pytest.fixture(params=["dev", "prod"])
def env(request):
    if request.param == "prod" and not os.getenv("ALLOW_PROD"):
        pytest.skip("prod disabled")
    return request.param
```

---

## 四、动态参数化：`pytest_generate_tests`

这是插件开发最常用的方式，可以在收集阶段根据配置、文件、环境生成参数。

```python
def pytest_generate_tests(metafunc):
    if "env" in metafunc.fixturenames:
        metafunc.parametrize("env", ["dev", "staging"], ids=["dev", "stg"])
```

### 结合你的项目：JSON 驱动的 API 用例

你配置里有 `api: JSON-defined API test cases`，可以这样实现：

```python
# src/pytest_myplugin/plugin.py
import json
from pathlib import Path
import pytest


def pytest_addoption(parser):
    parser.addoption(
        "--api-cases",
        action="store",
        default="cases/api.json",
        help="path to API cases JSON",
    )


def pytest_generate_tests(metafunc):
    if "api_case" not in metafunc.fixturenames:
        return

    path = Path(metafunc.config.getoption("--api-cases"))
    if not path.exists():
        return

    cases = json.loads(path.read_text(encoding="utf-8"))
    metafunc.parametrize(
        "api_case",
        cases,
        ids=[c.get("name", f"case-{i}") for i, c in enumerate(cases)],
        indirect=True,
    )


@pytest.fixture
def api_case(request):
    return request.param
```

用户测试：

```python
import pytest

@pytest.mark.api
def test_api_case(api_case):
    assert api_case["method"] in {"GET", "POST"}
```

运行：

```bash
pytest --api-cases cases/smoke.json -m api
pytest --collect-only -q   # 先看生成了哪些用例
```

## 五、最佳实践

### 1. 参数数据外置，但别过度

- 少量参数：直接写在 `parametrize` 里，可读性最好。
- 大量参数：放 JSON/YAML/CSV，用 `pytest_generate_tests` 加载。
- 不要把复杂逻辑塞进参数列表，参数列表应该是“数据”，不是“代码”。

### 2. ID 要短、稳定、可过滤

```python
ids=["login-ok", "login-bad-pwd", "login-locked"]
```

避免：
- 自动生成的 `test_api[case0]`，看不出含义。
- ID 里带空格、斜杠，`-k` 过滤麻烦。

### 3. 控制组合爆炸

- 多层 `parametrize` 叠加是笛卡尔积，数量容易失控。
- 用 `pytest --collect-only -q` 先看生成数量。
- 用 marker + `-m` 分组跑，用 `-k` 按 ID 过滤。

### 4. 不要共享可变参数对象

```python
# ❌ 同一个 dict 被所有测试共享，测试里改了会互相污染
@pytest.mark.parametrize("data", [{"a": 1}, {"a": 2}])
def test_data(data):
    data["a"] += 1
```

需要可变对象时，用工厂 fixture 或 `copy.deepcopy`。

### 5. 参数化 fixture 的 scope 要小心

- `scope="session"` + `params`：每个参数值在整个会话只创建一次，多个测试共享同一实例。
- 如果参数值对应的资源有状态，建议用 `function` scope。

### 6. 异步测试

配合 `pytest-asyncio`：

```python
@pytest.mark.parametrize("url", ["/a", "/b"])
@pytest.mark.asyncio
async def test_async(url):
    ...
```

### 7. 查看与调试

```bash
pytest --collect-only -q          # 看生成了哪些参数化用例
pytest --setup-show               # 看 fixture 和参数化 setup 顺序
pytest -k "production"            # 按 ID 过滤
```

## 六、常见陷阱

| 陷阱 | 问题 | 正确做法 |
| :--- | :--- | :--- |
| 参数名和 fixture 冲突 | 注入错对象 | 参数名不要和已有 fixture 重名 |
| `indirect` 用错 | 参数没传给 fixture | 确认 `indirect=True` 或 `indirect=["name"]` |
| 多层 parametrize 叠加 | 测试数量爆炸 | 先算笛卡尔积，必要时拆测试 |
| 参数是可变对象 | 测试间污染 | 用工厂 fixture 或深拷贝 |
| 在参数列表里做重计算 | 收集阶段就变慢 | 用 `pytest_generate_tests` 按需加载 |
| 参数化 fixture scope 太大 | 状态共享出问题 | 有状态资源用 `function` scope |
| 插件无条件覆盖用户参数化 | 用户无法控制 | 先检查 `metafunc.fixturenames`，只在需要时介入 |

---

## 七、插件开发中的参数化注意点

1. **只在用户请求你的 fixture 时介入**：

```python
def pytest_generate_tests(metafunc):
    if "myplugin_case" not in metafunc.fixturenames:
        return
    ...
```

2. **不要覆盖用户已有的 `parametrize`**。  
   如果用户已经手动参数化了同名参数，你的 hook 可能造成冲突。可以先检查：

```python
if metafunc.definition.get_closest_marker("parametrize"):
    return
```

但更稳妥的做法是：**让用户显式使用你的 fixture，你只参数化这个 fixture**。

3. **提供命令行选项控制行为**：

```python
parser.addoption("--myplugin-cases", default="cases.json")
```

4. **ID 要稳定**，便于用户用 `-k` 过滤。

5. **在插件里定义 `pytest_generate_tests` 时，注意它会对所有测试执行**，所以第一行必须是“是否包含我的 fixture”的判断。

---

## 总结

| 需求 | 用法 |
| :--- | :--- |
| 一个测试多组输入 | `@pytest.mark.parametrize` |
| 多个测试共享参数化资源 | `@pytest.fixture(params=...)` |
| 动态从文件/配置生成 | `pytest_generate_tests` |
| 给单个用例加 skip/xfail/slow | `pytest.param(..., marks=...)` |
| 参数先加工再给测试 | `indirect=True` + fixture |
| 参数传给 fixture | `request.param` |
| 避免组合爆炸 | 先 `--collect-only`，再用 `-m` / `-k` 分组 |
| 插件自动参数化 | `pytest_generate_tests` + 检查 `metafunc.fixturenames` |

**一句话**：`parametrize` 是“数据驱动测试”的入口，fixture params 是“资源参数化”，`pytest_generate_tests` 是“动态参数化”。静态数据用 `parametrize`，共享资源用 fixture params，外部数据/插件用 `pytest_generate_tests`。

# fixture应用

开发 fixture 的核心是：**把“测试前要准备的东西”和“测试后要清理的东西”封装成一个可复用的函数**。下面从零开始，逐步讲到插件级 fixture 的开发。

---

## 一、最小可用 fixture

```python
import pytest

@pytest.fixture
def sample_data():
    return [1, 2, 3]

def test_sum(sample_data):
    assert sum(sample_data) == 6
```

三要素：
1. 用 `@pytest.fixture` 装饰。
2. 函数名就是 fixture 名，测试函数通过**参数名**声明依赖。
3. `return` 的值会被注入到测试函数中。

---

## 二、带清理的 fixture：用 `yield`

这是**最推荐的写法**，能保证无论测试成功还是失败，清理代码都会执行。

```python
@pytest.fixture
def db_connection():
    conn = create_connection()      # setup
    yield conn                      # 注入给测试
    conn.close()                    # teardown，一定会执行
```

对比旧写法（不推荐）：

```python
# 旧写法：需要 request.addfinalizer，容易漏
@pytest.fixture
def db_connection(request):
    conn = create_connection()
    request.addfinalizer(conn.close)
    return conn
```

**要点**：
- `yield` 之前是 setup，之后是 teardown。
- teardown 里不要抛异常，否则会掩盖测试本身的失败。
- 如果需要传递异常信息，可以用 `try/finally` 包裹。

## 三、控制作用域 `scope`

作用域决定 fixture 的**创建和销毁频率**：

```python
@pytest.fixture(scope="session")   # 整个测试会话一次
def db_pool():
    pool = create_pool()
    yield pool
    pool.close()

@pytest.fixture(scope="module")    # 每个测试文件一次
def config():
    return load_config()

@pytest.fixture(scope="class")     # 每个测试类一次
def class_resource():
    ...

@pytest.fixture(scope="function")  # 每个测试函数一次（默认）
def temp_file(tmp_path):
    ...
```

**选择原则**：

| 资源特征 | 推荐 scope |
| :--- | :--- |
| 昂贵、可共享、无状态 | `session` |
| 模块级配置、只读数据 | `module` |
| 类内共享的对象 | `class` |
| 可变状态、需要隔离 | `function` |

**关键规则**：高 scope 的 fixture **不能依赖**低 scope 的 fixture。

```python
# ❌ 错误：session 依赖 function
@pytest.fixture(scope="session")
def bad(temp_file):   # temp_file 是 function 级
    ...

# ✅ 正确：function 依赖 session
@pytest.fixture
def good(db_pool):    # db_pool 是 session 级
    ...
```

## 四、fixture 之间的依赖

fixture 可以互相依赖，pytest 会自动按依赖顺序解析。

```python
@pytest.fixture(scope="session")
def api_base_url():
    return "https://api.example.com"

@pytest.fixture(scope="session")
def api_client(api_base_url):
    client = APIClient(api_base_url)
    yield client
    client.close()

@pytest.fixture
def authenticated_client(api_client, env_name):
    api_client.login(env=env_name)
    return api_client
```

**依赖解析规则**：
- 同一个测试函数依赖多个 fixture 时，pytest 会构建依赖图，按拓扑顺序执行。
- 相同 scope 的 fixture，按声明顺序执行。
- 不要写循环依赖，pytest 会报错。

## 五、参数化 fixture

让一个 fixture 提供多组数据，依赖它的测试会自动跑多次。

```python
@pytest.fixture(params=["dev", "staging", "prod"])
def env_name(request):
    return request.param

def test_api(env_name):
    assert call_api(env_name) == 200
# 自动跑 3 次：dev、staging、prod
```

**带 ID 的参数化**（让测试名更可读）：

```python
@pytest.fixture(params=[
    pytest.param("dev", id="development"),
    pytest.param("staging", id="staging"),
    pytest.param("prod", id="production"),
])
def env_name(request):
    return request.param
```

**动态跳过某些参数**：

```python
@pytest.fixture(params=["dev", "staging", "prod"])
def env_name(request):
    if request.param == "prod" and not os.getenv("ALLOW_PROD"):
        pytest.skip("prod tests disabled")
    return request.param
```

## 六、间接参数化 `indirect`

有时你想把参数化数据传给 fixture，让 fixture 加工后再给测试用。

```python
@pytest.fixture
def user(request):
    # request.param 来自测试的间接参数化
    return {"name": request.param, "id": hash(request.param)}

@pytest.mark.parametrize("user", ["alice", "bob"], indirect=True)
def test_user(user):
    assert user["name"] in ["alice", "bob"]
```

`indirect=True` 表示：参数不直接传给测试，而是传给同名 fixture。

## 七、使用 `request` 对象

`request` 是 fixture 的“运行时上下文”，提供了很多能力。

### 7.1 读取测试信息

```python
@pytest.fixture
def log_test_name(request):
    print(f"Running: {request.node.name}")
```

### 7.2 读取命令行选项

```python
@pytest.fixture(scope="session")
```

### 7.3 读取 marker

```python
@pytest.fixture
def browser(request):
    if request.node.get_closest_marker("ui"):
```

### 7.4 动态添加 finalizer

```python
@pytest.fixture
def resource(request):
    r = create()
    request.addfinalizer(r.cleanup)
    return r
```

### 7.5 访问其他 fixture（不推荐，但有时有用）

```python
@pytest.fixture
def dynamic(request):

    ...
```

## 八、自动使用 `autouse`

`autouse=True` 让 fixture 无需显式声明就自动生效。

```python
@pytest.fixture(autouse=True)
def reset_env():
    os.environ["TEST_MODE"] = "1"
    yield
    os.environ.pop("TEST_MODE", None)
```

**建议**：
- 只用于**全局性的、无副作用的**准备/清理。
- 不要滥用，否则依赖关系隐形，调试困难。
- 可以配合 scope 限定范围：

```python
@pytest.fixture(scope="session", autouse=True)
def setup_logging():
    logging.basicConfig(level=logging.INFO)
```

## 九、插件级 fixture 开发（你的场景）

你开发的是 **pytest 插件**，fixture 需要**暴露给用户使用**。这有几个额外要点。

### 9.1 在插件模块中定义 fixture

```python
# src/pytest_myplugin/plugin.py
import pytest

@pytest.fixture
def myplugin_client(request):
    """提供给用户的 fixture。"""
    config = request.config.getoption("--myplugin-endpoint")
    client = MyPluginClient(config)
    yield client
    client.close()
```

用户安装插件后，**无需 import**，直接在测试里用：

```python
def test_something(myplugin_client):
    assert myplugin_client.ping() == "pong"
```

### 9.2 命名约定

插件 fixture 建议加**前缀**，避免和用户自己的 fixture 冲突：

```python
@pytest.fixture
def myplugin_client():      # ✅ 好：有前缀
    ...

@pytest.fixture
def client():               # ❌ 差：太通用，容易冲突
    ...
```

### 9.3 在 conftest 中注册 fixture（仅本地测试用）

```python
# tests/conftest.py
pytest_plugins = ["pytest_myplugin.plugin"]
```

这只是本地测试时加载插件，**发布时必须靠 `pytest11` entry point**。

### 9.4 fixture 的文档

插件 fixture 是用户直接使用的 API，必须写好 docstring：

```python
@pytest.fixture
def myplugin_client(request):
    """
    Provide a configured client for the plugin.

    Reads ``--myplugin-endpoint`` from the command line.
    Automatically closes the client after the test.

    Yields:
        MyPluginClient: a ready-to-use client instance.
    """
```

## 十、结合你的项目：几个实用 fixture 示例

基于你的依赖（PyGithub、huggingface-hub），可以写这些 fixture：

## 十二、常见陷阱

| 陷阱 | 问题 | 正确做法 |
| :--- | :--- | :--- |
| `return` 代替 `yield` 做清理 | 清理不会执行 | 需要清理时用 `yield` |
| 高 scope 依赖低 scope | pytest 报错 | 调整 scope 或拆分 fixture |
| fixture 里改可变状态 | 污染其他测试 | 每次返回新对象，或用 function scope |
| `autouse` 滥用 | 依赖隐形 | 显式声明依赖 |
| fixture 名太通用 | 和用户冲突（插件场景） | 加插件前缀 |
| teardown 抛异常 | 掩盖测试失败 | teardown 里 try/except |
| fixture 里做重操作但 scope 太小 | 测试变慢 | 提升 scope 或缓存 |

## 十三、完整示例：一个生产级 fixture

```python
@pytest.fixture(scope="session")
def api_client(request):
    """
    提供带认证的 API 客户端。

    从命令行 ``--api-endpoint`` 读取地址，
    从环境变量 ``API_TOKEN`` 读取 token。

    整个测试会话共享一个客户端，会话结束后关闭。
    """
    endpoint = request.config.getoption("--api-endpoint")
    token = os.getenv("API_TOKEN")

    if not endpoint:
        pytest.skip("--api-endpoint not provided")

    client = APIClient(endpoint, token=token)

    # 健康检查
    try:
        client.ping()
    except ConnectionError:
        pytest.skip(f"API at {endpoint} is unreachable")

    yield client

    client.close()


@pytest.fixture
def fresh_user(api_client):
    """为每个测试创建一个独立用户，测试后删除。"""
    user = api_client.create_user()
    yield user
    api_client.delete_user(user.id)
```

## 总结

开发 fixture 的要点可以浓缩成一张表：

| 需求 | 写法 |
| :--- | :--- |
| 提供数据 | `return value` |
| 需要清理 | `yield value` + teardown |
| 共享昂贵资源 | `scope="session"` |
| 提供多组数据 | `params=[...]` |
| 依赖其他 fixture | 在参数中声明 |
| 读取命令行/配置 | `request.config.getoption(...)` |
| 根据 marker 分支 | `request.node.get_closest_marker(...)` |
| 自动生效 | `autouse=True`（慎用） |
| 插件对外暴露 | 加前缀 + 写 docstring |
| 调试 | `pytest --setup-show` |

**一句话**：fixture 的本质是**依赖注入 + 生命周期管理**。把“准备什么、给什么、清理什么”想清楚，代码自然就写对了。
