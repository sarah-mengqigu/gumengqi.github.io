# 项目配置文件 pyproject.toml

最新开发项目推荐使用pyproject.toml，可以复用python现代项目中的[build-system]声明构建后端机器依赖,[project]定义项目元数据、依赖等。

单独定义[tool.pytest.*],对pytest可以单独配置：

```ini
[project.entry-points.pytest11]
my-plugin-name = "my_plugin_module.plugin"

[tool.pytest.ini_options]
minversion = "7.0"
addopts = "-ra -q --strict-markers"
testpaths = ["tests"]
markers = [
    "slow: marks tests as slow",
    "integration: integration tests",
]
```

# conftest.py插件注册

## pytest定义的整体生命周期

pytest 启动后大致经历：

```text
启动配置
  ↓
收集阶段（Collection）
  ↓
运行阶段（Run）
  ↓
报告与退出
```

其中，`conftest.py` 里的不同 hook 分布在不同的阶段：

| 阶段 | 典型 hook / 行为 |
| :--- | :--- |
| 启动配置 | `pytest_addoption`、`pytest_configure` |
| **收集阶段** | `pytest_collect_file`、`pytest_generate_tests`、`pytest_collection_modifyitems` |
| **运行阶段** | `pytest_runtest_setup`、`pytest_runtest_call`、`pytest_runtest_teardown`、`pytest_runtest_makereport` |
| 结束 | `pytest_unconfigure`、`pytest_sessionfinish` |

---

## 收集阶段（Collection）

收集阶段的任务是：**找出所有测试，并生成测试项（test items）**。

具体包括：

1. 从命令行指定的路径（或 `testpaths`）开始扫描。
2. 根据命名规则识别测试文件、测试类、测试函数。
3. 解析 `@pytest.mark.parametrize`，为每组参数生成一个测试项。
4. 执行 `pytest_generate_tests`，动态生成参数化。
5. 执行 `pytest_collection_modifyitems`，对测试项进行过滤、排序、加 marker。
6. 最终产出一个 `items` 列表，每个 `item` 代表一个即将运行的测试。


### 常见 hook

```python
def pytest_collection_modifyitems(config, items):
    """收集完成后，对 items 做最后调整。"""
    # items 是收集到的所有测试项
    for item in items:
        if "slow" in item.keywords:
            item.add_marker(pytest.mark.skip(reason="slow test"))
```

```python
def pytest_generate_tests(metafunc):
    """为测试动态生成参数。"""
    if "env" in metafunc.fixturenames:
        metafunc.parametrize("env", ["dev", "staging", "prod"])
```

### 如何观察收集阶段

```bash
pytest --collect-only -q
```

只收集、不运行，输出所有测试项：

```text
tests/test_api.py::test_login[dev]
tests/test_api.py::test_login[staging]
tests/test_api.py::test_login[prod]
```


## 运行阶段（Run / Execution）

运行阶段的任务是：**逐个执行收集阶段生成的测试项**。

每个测试项的执行又分为三个子阶段：

```text
setup    → 准备（fixture 初始化）
call     → 执行测试函数
teardown → 清理（fixture 清理）
```

对应 pytest 的 hook：

| 子阶段 | hook | 说明 |
| :--- | :--- | :--- |
| setup | `pytest_runtest_setup` | 测试函数执行前，初始化 fixture |
| call | `pytest_runtest_call` | 真正执行测试函数 |
| teardown | `pytest_runtest_teardown` | 测试结束后，清理 fixture |
| 报告 | `pytest_runtest_makereport` | 生成测试结果报告 |

fixture 在运行阶段才真正实例化：

- `yield` 之前的 setup 在 `setup` 子阶段执行。
- `yield` 之后的 teardown 在 `teardown` 子阶段执行。

### 作用域与运行阶段

fixture 的 `scope` 决定了它在运行阶段的哪个层级初始化：

| scope | setup 时机 | teardown 时机 |
| :--- | :--- | :--- |
| `function` | 每个测试项 setup 时 | 每个测试项 teardown 时 |
| `class` | 每个测试类第一个测试 setup 前 | 该类最后一个测试 teardown 后 |
| `module` | 每个测试文件第一个测试 setup 前 | 该文件最后一个测试 teardown 后 |
| `session` | 整个运行阶段开始时 | 整个运行阶段结束时 |

精细限定fixture的scope在module可以在不同的测试目录层级下创建conftest.py，在其中定义fixture

### conftest.py 中的执行顺序

```python
def pytest_configure(config):
    # 启动配置阶段，最早执行
    ...

def pytest_collection_modifyitems(config, items):
    # 收集阶段，fixture 还没实例化
    ...

@pytest.fixture
def client():
    # 运行阶段，每个测试 setup 时才执行
    ...

```

# 交叉能力分析

`[tool.pytest.ini_options]` 是**声明式静态配置**，`conftest.py` 是**命令式编程接口**。
两者提供的能力有重叠

## 重叠的能力

| 功能 | `pyproject.toml` 配置 | `conftest.py` 等价写法 |
| :--- | :--- | :--- |
| **注册 marker** | `markers = ["slow: ..."]` | `config.addinivalue_line("markers", "slow: ...")` |
| **过滤警告** | `filterwarnings = ["error"]` | `warnings.filterwarnings("error")` |
| **添加默认参数** | `addopts = "-ra -q"` | `config.option.verbose = 1` 等逐项设置 |
| **忽略测试路径** | `norecursedirs = [...]` | `collect_ignore` / `collect_ignore_glob` |
| **设置测试路径** | `testpaths = ["tests"]` | `pytest_collection_modifyitems` 里过滤 |
| **加载插件** | `addopts = "-p myplugin"` | `pytest_plugins = ["myplugin"]` |
| **修改日志行为** | `log_cli`, `log_level` | `pytest_configure` 里操作 `logging` |
| **设置 pythonpath** | `pythonpath = ["src"]` | `sys.path.insert(0, "src")` |

### 只有 `conftest.py` 支持的能力

| 能力 | 说明 |
| :--- | :--- |
| **定义 fixture** | ini 里根本没有 fixture 的概念 |
| **实现 hook** | `pytest_collection_modifyitems`、`pytest_runtest_setup` 等 |
| **添加命令行选项** | `pytest_addoption` |
| **动态条件逻辑** | 根据环境变量、CI 状态、Python 版本分支 |
| **按目录层级覆盖** | 子目录的 `conftest.py` 可以覆盖父级的 fixture/hook |
| **访问运行时对象** | `request`、`config`、`item`、`session` 等 |

### 只有 `pyproject.toml` 支持的能力

| 能力 | 说明 |
| :--- | :--- |
| **声明项目级元数据** | `minversion`、`required_plugins` |
| **静态路径配置** | `testpaths`、`norecursedirs` |
| **声明式 warning 过滤** | 比代码更直观 |
| **插件默认启用/禁用** | `-p no:cacheprovider` 等 |
| **CI 无关的统一配置** | 不依赖代码执行 |

---

## 关键差异：**声明式 vs 命令式**

| 维度 | `[tool.pytest.ini_options]` | `conftest.py` |
| :--- | :--- | :--- |
| **性质** | 静态配置，声明式 | 代码，命令式 |
| **何时生效** | pytest 启动时读取 | 收集/运行时执行 |
| **可调试性** | 看得见，改起来直观 | 需要读代码 |
| **动态能力** | 无（除了环境变量插值） | 完全动态 |
| **作用域** | 整个项目 | 按目录层级作用 |
| **可复用性** | 复制配置 | 可以打包成插件 |
| **能否条件分支** | 不能 | 可以 |


## 该怎么选：实用原则

### 优先用 `pyproject.toml` 的情况

- 配置是**静态的、项目级的**，不依赖运行时状态
- 例如：`markers`、`testpaths`、`addopts`、`filterwarnings`、`log_cli`
- 理由：可见性高、不执行代码、易于审查

### 必须用 `conftest.py` 的情况

- 需要**根据环境/条件动态变化**
- 需要**定义 fixture**
- 需要**实现 hook**
- 需要**按目录层级覆盖初始化动作**
- 需要**访问 pytest 运行时对象**

### 两者都用但要注意优先级的情况

当同一功能两边都配置时，行为通常是**叠加**而非覆盖：

```toml
# pyproject.toml
markers = ["slow: ..."]
```

```python
# conftest.py
def pytest_configure(config):
    config.addinivalue_line("markers", "integration: ...")
```

结果：两个 marker 都被注册，**不冲突**。

但如果是 `filterwarnings`，两边都设置，顺序会影响最终行为——**后应用的规则优先**，而 conftest 的 `pytest_configure` 在 ini 之后执行，所以 conftest 里的规则会覆盖 ini 中冲突的规则。


## 总结

| 问题 | 答案 |
| :--- | :--- |
| 是否有重叠？ | **有**，约 8 类配置项功能重叠 |
| 重叠时用哪个？ | 静态配置优先用 ini；动态/条件/层级覆盖用 conftest |
| 能否完全互相替代？ | **不能**。fixture、hook、`pytest_addoption` 只能写在 conftest |
| 会互相冲突吗？ | 大多数情况是**叠加**；`filterwarnings` 等顺序敏感项，conftest 后执行会覆盖 ini |
