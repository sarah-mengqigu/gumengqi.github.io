## 一、基于模型的测试：MBT

基于模型的测试（Model-Based Testing, MBT）并不是新概念。它的核心思想非常优雅：先用形式化模型描述系统行为，再由算法自动生成测试用例，从根本上解决人工设计测试用例覆盖率不足、维护成本高的问题。

### 1.1 传统MBT：叫好不叫座的技术高地

三十年来，MBT始终停留在“实验室技术”和“高合规行业专属工具”的位置。原因在于它的三重门槛：

**门槛一：建模成本高。** 传统MBT要求用UML Statechart、B方法、Z语言、Spec#等形式化语言建模。这些语言对业务专家不友好，对测试工程师也是陡峭的学习曲线。写一个完整状态机要几天，业务变化一次又要重写。

**门槛二：工具链复杂。** 商业工具（Conformiq、Spec Explorer）昂贵且封闭；开源工具（GraphWalker、ModelJUnit）学习曲线陡峭。小团队要花几个月才能搭建起可用环境，ROI周期往往长于产品生命周期。

**门槛三：与敏捷冲突。** 形式化建模需要前置规划，而敏捷迭代两周一个Sprint。模型还没写完，需求已经变了。MBT从赋能工具变成了流程负担。

结果就是，MBT在航空航天、汽车电子、通信协议等强合规、长周期、大团队场景有效，在Web/移动/互联网业务、中小团队、快速迭代场景几乎无效。

## AI辅助测试阶段回顾
ChatGPT横空出世到2026年下半年，软件测试工程也在随着模型能力的演变

很多时候在用AI处理大量低质量的资产，真实团队的测试资产质量不可避免的参差不齐。这对AI理解业务造成的瓶颈。无论在AI辅助上投入多少，瓶颈不突破，测试的工作量实质上不会减少。

## 五、模型作为Spec的SDT（Spec-Driven-Test）实践

至此，我们有了YAML模型，有了NetworkX算法，有了自包含的Python脚本。这三者组合起来，形成一个完整的**SDT（Spec-Driven-Test）实践**——**把模型本身作为规格说明（Spec），驱动测试的生成与评估**。

它包含三个核心环节：

### 5.1 状态机分析

第一个环节是对状态机本身进行数理分析，回答“这个状态机的结构如何”。

**输出内容包括**：

- **基础统计**：总状态数、总转换数、初始状态、终止状态
- **连通性**：是否强连通、强连通分量分组
- **状态详情**：每个状态的入度、出度、PageRank、所属SCC
- **关键状态识别**：最重要的状态（PageRank最高）、最频繁的转换
- **复杂度指标**：图密度、平均分支因子

**现实指导意义**：

- 大型SCC（多状态循环）是复杂功能模块，需要重点测试循环逻辑和边界条件
- 高PageRank状态是核心枢纽，需要重点测试和监控
- 初始/终止状态需要特别的验证逻辑

用一条命令即可完成：

```bash
python state_machine_analyzer.py analyze --yaml state.yaml
```

### 5.2 测试路径生成

第二个环节是生成测试路径，回答“应该测试哪些状态转换序列”。

支持**五种路径生成策略**，各有优劣：

**DFS路径**：

- 特征：单条长路径，倾向走尽可能多的状态
- 优势：执行效率高、测试用例简单清晰、资源消耗少
- 劣势：可能错过重要循环路径、循环测试不充分、边界条件覆盖不足
- 适用场景：冒烟测试、回归测试主路径

**SCC循环路径**：

- 特征：为每个强连通分量生成循环路径
- 优势：充分测试状态循环和复杂交互、覆盖所有可能的循环路径、更容易发现循环相关缺陷
- 劣势：可能产生多条测试用例、执行时间较长、需要更多资源
- 适用场景：完整性测试、性能测试、边界测试

**欧拉路径**：

- 特征：遍历每条边恰好一次（当图满足欧拉条件时）
- 优势：路径最短、测试用例数量最少、覆盖所有转换一次
- 劣势：条件严格（许多实际状态机不满足）
- 适用场景：转换覆盖测试

**贪心覆盖路径**：

- 特征：优先选择覆盖未访问边/节点的下一步
- 优势：适用于任意图、覆盖效率较高
- 劣势：不保证最优解
- 适用场景：通用场景

**混合策略（推荐）**：

- 组合DFS和SCC路径，按边覆盖度排序，贪心去重
- 在覆盖度和路径数量之间取得平衡

**从测试覆盖角度的重要结论**：

| 维度 | SCC路径 | DFS路径 |
|------|---------|---------|
| 深度覆盖 | 高（循环充分） | 中 |
| 缺陷发现（循环/资源泄漏/并发） | 高 | 低 |
| 测试效率 | 中 | 高 |
| 测试用例数量 | 多 | 少 |
| 冒烟测试 | 不适合 | 适合 |
| 完整性测试 | 适合 | 不适合 |

**推荐实践：混合使用两类路径**——DFS覆盖主线，SCC覆盖循环；根据测试阶段动态调整策略。

用一条命令即可生成：

```bash
python state_machine_analyzer.py paths --yaml state.yaml --strategy hybrid --max-paths 5
```

### 5.3 测试覆盖度评估

第三个环节是评估测试的覆盖完整性，回答“哪些状态和转换还没被覆盖”。

**输出内容包括**：

- **覆盖度摘要**：总状态数/已覆盖数、总转换数/已覆盖数、覆盖率百分比
- **覆盖缺口**：未覆盖的状态列表、未覆盖的转换列表
- **改进建议**：基于未覆盖情况，自动推荐应采用的策略

**现实指导意义**：

- 未覆盖的高频转换是测试盲区，需要补充用例
- 覆盖度不足时，可切换策略或增加路径数量

用一条命令即可评估：

```bash
python state_machine_analyzer.py coverage --yaml state.yaml --paths paths.json
```

### 5.4 从路径到用例：LLM的语义化

数理分析给出的是**技术路径**（节点序列 + action）。但从测试工程师的角度，这些路径还需要转化为**可执行的业务用例**——预置条件、测试步骤、预期结果、优先级。

这正是LLM的用武之地。给LLM的提示词可以很简单：

> 基于以下测试路径信息，生成详细的测试用例：
>
> 路径: init → running → stopped → running → terminated
> 边信息:
> - init → running: CreateInstance Succeed (OS安装成功)
> - running → stopped: PowerDown (关机成功)
> - stopped → running: api_power_on (开机成功)
> - running → terminated: DeleteInstance Succeed (卸载OS成功)
>
> 请为这个路径生成包含以下内容的测试用例：
> 1. 测试用例名称
> 2. 预置条件
> 3. 测试步骤
> 4. 预期结果
> 5. 优先级

LLM会生成一份结构化的用例文档：

```
### TC-001: 服务器正常关机重启流程

**优先级**: P0
**业务场景**: 运维人员对运行中的服务器执行关机维护，维护完成后重新开机

**预置条件**:
- 服务器实例已创建且处于"运行中"状态
- 服务器已安装 CentOS 7.9 操作系统
- 运维平台可正常访问

**测试步骤**:
1. 在运维平台选择目标服务器，点击"关机"
   - 预期：接收到 PowerDown 请求
2. 等待关机操作完成
   - 预期：状态从"运行中"变为"已关机"
3. 在运维平台点击"开机"
   - 预期：接收到 api_power_on 请求
4. 等待开机操作完成
   - 预期：状态从"已关机"变回"运行中"

**验证点**:
- 状态流转: running → stopped → running
- 关键动作: PowerDown, api_power_on
- 数据一致性: 关机前后服务器配置保持不变
```

这就是SDT的完整闭环：

- **Python负责数理分析**：状态机结构、路径生成、覆盖度评估
- **LLM负责语义生成**：把技术路径翻译成业务语言用例
- **模型作为Spec**：YAML模型既是规格说明，又是测试生成的输入，又是回归验证的基准

### 5.5 另一种建模

本文作者另一篇实践[《从组合爆炸到精准覆盖：IaaS解决方案测试的场景空间建模与工程化实践》](https://sarah-mengqigu.github.io/gumengqi.github.io/test-engineering/2026/09/09/test-engineering1.html
)同样也使用了MBT的方法。

区别于本文中状态机模型的业务，针对的是复杂场景组合的建模。但建模作为Spec的SDT范式是一脉相承的：

算法负责数理分析：状态机结构分析、路径生成、场景空间分析、双维覆盖度评估
LLM负责语义生成：把“路径×场景”翻译成业务语言的、可交付的测试用例
模型作为Spec：
- 状态机YAML是时序维度的规格说明
- 场景平面YAML是空间维度的规格说明
- 两者共同构成完整的解决方案规格，既是测试生成的输入，又是回归验证的基准

## 六、人的能力跃升

当工具链条足够成熟后，真正的瓶颈从“工具怎么用”转向“人怎么定位”。AI辅助MBT带来的最大价值，不只是效率提升，更是**测试工程师能力结构的重塑**。

### 6.1 业务定义能力：从测试执行到SDD-SDT

传统测试工程师的核心能力是根据需求写用例，根据用例执行测试。在新范式中，测试工程师需要具备**规格驱动开发/测试（SDD-SDT, Spec-Driven Development / Spec-Driven Test）**的思维：

- 能够将模糊的业务描述抽象为**状态机模型**：识别状态、识别转换、识别触发条件
- 能够用YAML等**可执行规格**表达业务规则
- 能够判断“哪些业务适合用状态机建模”、“哪些状态应该合并/拆分”

这是一种**建模能力**，它介于产品经理的“需求表达”和工程师的“代码实现”之间。测试工程师对“边界条件”和“异常路径”的敏感度，使他们天生适合做这件事。

### 6.2 算法/数学知识：从黑盒使用者到白盒决策者

AI可以生成算法代码，但**判断算法是否适用**是人的职责。人类需要掌握理解图论、矩阵运算、概率论这些更为抽象的知识，能力关键不是会推导公式，而是知道“什么时候用什么工具”。这种判断力，是AI无法替代的。

### 6.3 工具选型：开源还是自造？

传统MBT时代的选择是“用GraphWalker还是Conformiq”，非此即彼。AI时代的选择更丰富，也更需要判断力：

**选择的关键考量**：

- 建模成本 vs 使用收益
- 维护成本 vs 长期价值
- 通用性 vs 贴合度

一个务实的建议是：**从自研脚本起步，验证价值后再决定是否引入通用工具**。AI让自研的成本降低了一个数量级，“量体裁衣”变得可行。

### 6.4 方案决策：模型抽象程度与人力成本估算

最后，也是最难的，是**方案决策能力**。AI提效带来的人员结构压缩要求方案决策者往下要了解业务细节，往上要评估测试资源的投入成本：

**模型抽象程度决策**：

- 建模太细：状态爆炸，路径组合不可控，维护成本高
- 建模太粗：遗漏关键细节，测试覆盖不足
- 判断标准：**如果模型能手动列出所有路径，就不需要MBT**；如果无法手工枚举，就需要建模

**人力成本估算**：

- 建模：YAML描述状态机（小时级）
- 工具：AI辅助生成脚本（天级）
- 用例：LLM生成 + 人工审查（小时级）
- 维护：模型变更时重新生成（分钟级）

**ROI判断**：

- 传统方式：单个状态机建模 + 路径设计 + 用例编写 + 维护 ≈ 9人天
- 新方式：YAML建模 + 脚本生成 + LLM用例 + 维护 ≈ 0.85人天
- 效率提升约**10倍**，覆盖度从约60%提升到约95%

### 6.5 能力结构的重塑

| 能力维度 | 传统测试工程师 | AI时代MBT工程师 |
|---------|--------------|----------------|
| 业务理解 | 深度理解流程 | 深度理解 + 抽象为状态机 |
| 建模能力 | 不要求 | 能用YAML/自然语言描述模型 |
| 编程能力 | 会写测试脚本 | 会用AI生成并审查框架代码 |
| 数学基础 | 不要求 | 懂图论、矩阵、概率论概念 |
| AI协作 | 不涉及 | 熟练用LLM做代码和用例生成 |
| 工具开发 | 用现成工具 | 快速自研场景化工具 |
| 方案决策 | 执行既定方案 | 判断抽象程度与ROI |

**AI把用例文本编写、用例脚本开发的工作接走了，留给人的是更靠近业务本质的建模、判断和决策**。测试工程师从“测试执行者”跃升为“测试建模者”和“质量架构师”。

## 结语：测试左移和SDD的一种落地范式

MBT从来不是技术问题，而是成本问题。

**传统MBT的困境**是：建模成本高 × 工具门槛高 × 迭代冲突 = 不可行。

**AI时代MBT的机遇**是：LLM降低建模门槛、LLM降低开发门槛、LLM降低维护门槛，三者叠加，成本下降10-100倍。

这意味着：小团队也能用MBT，敏捷迭代也能用MBT，每个测试工程师都能拥有“自己的MBT框架”。

技术基础没有变——状态机、图论、路径覆盖，这些数学工具几十年前就已成熟。真正变化的是**谁可以使用它**。过去需要专家团队、专门工具、周级建模周期，现在只需要一个测试工程师、一个YAML文件、一个Python脚本、一个LLM。门槛的降低，让MBT从“实验室技术”走向“工程实践”。

这个项目的价值，不在于发明了新技术，而在于把传统MBT从“少数专家的奢侈工具”变成了“测试工程师的日常武器”。在AI时代，**让好技术真正被用起来**，往往比发明新技术更有价值。

关键不是“用不用MBT”，而是“**你能不能快速为业务定制一个MBT框架**”。

而这，恰恰是AI时代测试开发工程师的核心竞争力。
