# 一、基于模型的测试：MBT

基于模型的测试（Model-Based Testing, MBT）并不是新概念。它的核心思想非常优雅：先用形式化模型描述系统行为，再由算法自动生成测试用例，从根本上解决人工设计测试用例覆盖率不足、维护成本高的问题。

三十年来，MBT始终停留在“实验室技术”和“高合规行业专属工具”的位置。原因在于它的三重门槛：

**门槛一：建模成本高。** 传统MBT要求用UML Statechart、B方法、Z语言、Spec#等形式化语言建模。这些语言对业务专家不友好，对测试工程师也是陡峭的学习曲线。写一个完整状态机要几天，业务变化一次又要重写。

**门槛二：工具链复杂。** 商业工具（Conformiq、Spec Explorer）昂贵且封闭；开源工具（GraphWalker、ModelJUnit）学习曲线陡峭。小团队要花几个月才能搭建起可用环境，ROI周期往往长于产品生命周期。

**门槛三：与敏捷冲突。** 形式化建模需要前置规划，而敏捷迭代两周一个Sprint。模型还没写完，需求已经变了。MBT从赋能工具变成了流程负担。

结果就是，MBT在航空航天、汽车电子、通信协议等强合规、长周期、大团队场景有效，在Web/移动/互联网业务、中小团队、快速迭代场景几乎无效。

# 二、AI辅助测试阶段回顾

ChatGPT横空出世到2026年下半年，AI辅助测试工程经历了一条清晰的能力演进历程。

## 第一阶段：让模型懂测试

**核心命题**：如何让通用大模型理解测试领域的业务语义？

这个阶段的根本矛盾是——通用模型懂语言，但不懂测试。它不知道什么是“状态机转换”，不知道“预置条件”和“测试步骤”的区别，不知道业务领域的专业术语。解决这个矛盾，经历了两个子阶段。

### 1.1 模型微调阶段

收集测试用例、测试脚本等数据，做数据清洗，进行模型微调。

**典型做法**：
- 把历史测试用例整理成“输入-输出”对
- 用测试脚本代码做代码补全微调
- 让模型学会测试领域的表达方式

**解决的问题**：
- 模型能生成格式正确的测试用例
- 模型能理解测试术语（预置条件、步骤、预期结果）
- 模型能写出符合团队规范的测试脚本

**暴露的新瓶颈**：
- **数据量不够**：微调需要大量高质量样本，但团队历史资产有限
- **知识更新慢**：产品迭代快，微调一次要几周，模型知识很快过期
- **幻觉严重**：模型会“编造”不存在的业务逻辑，因为它只学了格式，没学知识
- **成本高**：每次产品变更都要重新微调，ROI 不划算

**阶段结论**：微调解决了“格式”问题，但没解决“知识”问题。模型会写测试用例的“样子”，但不知道业务到底是什么。

### 1.2 RAG阶段

产品设计文档、测试资产文档、需求文档等语料治理，构建向量知识库，通过检索增强生成。

**典型做法**：
- 把产品文档、接口文档、历史用例全部向量化
- 用户提问时，先从知识库检索相关片段
- 把检索结果作为上下文喂给模型，让模型基于真实文档生成

**解决的问题**：
- **知识实时性**：文档更新后，RAG 知识库同步更新，不用重新训练
- **幻觉降低**：模型基于检索到的真实文档生成，而不是凭空编造
- **领域适应**：通过检索测试资产文档，模型能理解具体业务逻辑

**暴露的新瓶颈**：
- **语料质量参差不齐**：真实团队的测试资产质量参差不齐，垃圾进垃圾出
- **文档与代码脱节**：文档写的是“应该怎样”，代码实现的是“实际怎样”，两者经常不一致
- **检索精度有限**：向量检索只能找到“语义相似”的片段，找不到“逻辑相关”的知识
- **静态知识 vs 动态流程**：RAG 提供的是静态知识，但测试需要的是动态执行能力

**阶段结论**：RAG 解决了“知识”问题，但没解决“执行”问题。模型知道了业务是什么，但还不能真正“做”测试。


## 第二阶段：让模型用工具

### 2.1 Skill阶段

用自然语言描述流程规范，用脚本提供解析和工具调用能力。

**典型做法**：
- 把测试流程写成自然语言描述（“先创建实例，再安装系统，最后验证状态”）
- 为每个原子操作提供脚本工具（create_instance.py、install_os.py、check_status.py）
- 模型根据流程描述，自主选择工具并编排执行顺序

**解决的问题**：
- **执行能力**：模型从“生成文本”升级为“调用工具”
- **流程标准化**：自然语言描述流程，比代码更易读、易改
- **人机协作**：测试工程师写流程描述，模型负责执行细节

**暴露的新瓶颈**：
- **流程描述歧义**：自然语言有歧义，“先创建再安装”到底是串行还是并行？
- **工具选择困难**：当有几十个工具时，模型选错工具的概率急剧上升
- **错误恢复缺失**：工具调用失败后，模型不知道怎么重试或回滚
- **上下文窗口限制**：长流程需要多轮工具调用，上下文很快被撑爆

**阶段结论**：Skill 解决了“执行”问题，但没解决“自主编排”问题。模型能调用工具，但需要人告诉它每一步做什么。

### 2.2 Agent Harness阶段

用 Harness（约束框架）约束 Agent 行为，让模型自主规划、执行、反思、调整。

到这一阶段，**模型参数和 RAG 向量化的边际收益快速递减**。影响 Agent 行为质量的关键变量，已经从“模型能力”转移到了“约束框架（Harness）设计”。

**阶段结论**：Agent 解决了“自主编排”问题，但暴露了一个更根本的问题——**Agent 输出质量的天花板，不是模型能力，而是输入的 Spec 质量**。


## 第三阶段：让模型自己被测（AI Native）

当被测产品本身变成了 AI，测试的定位被重新定义

前两个阶段在讲“AI 怎么辅助测试”，这个阶段测对象从确定性系统变成了概率性系统。

**典型变化**：

| 维度 | 传统测试 | AI Native 测试 |
|------|---------|---------------|
| 被测对象 | 确定性系统 | 概率性系统（模型、Skill、Agent） |
| 测试方法 | 断言输出等于预期 | 评估输出的分布与边界 |
| 覆盖准则 | 代码覆盖率、路径覆盖率 | 语义覆盖率、场景覆盖率 |
| 通过标准 | 100% 通过 | 可接受的质量分布 |
| 回归策略 | 固定用例集 | 持续评估 + 边界监控 |

**核心挑战**：
- 概率性系统没有“正确答案”，只有“可接受范围”
- 测试用例本身也需要 AI 来生成（传统手工用例覆盖不了语义空间）
- 质量评估从“通过/失败”变成“评分/排序”


## 贯穿始终的暗线：Spec质量决定上限

回顾这条演进曲线，会发现一个被忽视的事实：

**从微调到 RAG，从 Skill 到 Agent，每一次能力跃升，都会把瓶颈从“AI 能不能做”转移到“人有没有准备好”。**

- 微调阶段，瓶颈是“有没有高质量训练数据”
- RAG 阶段，瓶颈是“有没有高质量领域文档”
- Skill 阶段，瓶颈是“有没有清晰的流程描述”
- Agent 阶段，瓶颈是“有没有结构化的 Spec”

于是，SDD、SDT 的思想逐渐清晰：**与其训练更垂直的模型，不如准备好更结构化的 Spec**。实践中人们发现，高质量的 Spec 文档比模型微调带来的效果更好、更稳定。

**无论 AI 辅助手段多先进，测试资产本身的质量才是决定上限的天花板**。真实团队的测试资产质量参差不齐，AI 在处理大量低质量资产时，对业务的理解必然受限。这意味着：在 AI 辅助上投入再多，如果资产质量这个瓶颈不突破，测试工作量的实质性减少就不会发生。


# 三、模型作为Spec的SDT（Spec-Driven-Test）实践

在
[《以状态机建模的测试工程能力提升实践》](https://sarah-mengqigu.github.io/gumengqi.github.io/test-engineering/2026/09/13/test-engineering4.html)
[《从组合爆炸到精准覆盖：IaaS解决方案测试的场景空间建模与工程化实践》](https://sarah-mengqigu.github.io/gumengqi.github.io/test-engineering/2026/09/09/test-engineering1.html)
两篇文章中，分别使用了测试建模中有两种典型形态：

* 状态机模型：描述系统在时间维度上如何演化。回答“系统在生命周期中经历了哪些状态，如何从一个状态转移到下一个状态”。典型场景如服务器生命周期、订单状态流转、审批流程等。

* 场景空间模型：描述系统在空间维度上如何适配。回答“系统在什么样的节点类型、网卡型号、组网形态、软件版本组合下运行”。典型场景如IaaS解决方案、多版本兼容测试、多局点部署验证等。

一类是时序维度的抽象，另一类是空间维度的抽象。

第一个环节是对模型本身进行数理分析，回答“这个模型的结构如何”。

# 状态机模型分析
输出内容包括：

基础统计：总状态数、总转换数、初始状态、终止状态

连通性：是否强连通、强连通分量分组

状态详情：每个状态的入度、出度、PageRank、所属SCC

关键状态识别：最重要的状态（PageRank最高）、最频繁的转换

复杂度指标：图密度、平均分支因子

---

现实指导意义：

大型SCC（多状态循环）是复杂功能模块，需要重点测试循环逻辑和边界条件

高PageRank状态是核心枢纽，需要重点测试和监控

初始/终止状态需要特别的验证逻辑

## 场景空间模型分析
输出内容包括：

维度清单：每个场景因子（节点类型、网卡型号、组网形态、云形态、软件版本、ring环阶段等）

取值分布：每个维度的典型取值数量，以及这些取值在现网中的分布（高频/低频/边缘）

场景向量空间规模：理论组合数 = 各维度取值的笛卡尔积

现网真实场景子集：从CMDB/监控中提取的、真实存在的场景向量

场景平面划分：将现网场景按架构分层聚类，形成可由同一套测试环境覆盖的“场景平面”

---

现实指导意义：

大约60%的理论组合在现网中并不存在，不必全测

约20%的组合仅存在于1-2个边缘局点，可按优先级取舍

真正的高频核心场景不到20%，必须优先覆盖

场景平面是连接“数理分析”与“环境资源”的桥梁

---

# 测试模型指导测试策略

完善的测试模型可以帮助TSE在每轮版本迭代中，清晰识别关键改动点，确定重点投入工作。

一位有经验的业务专家在脑海中沉淀着类似的建模蓝图，但通过数学语言精准描述后，这项能力能为一个外显的，可交流、可被AI理解的知识资产。

当AI辅助工具链条足够成熟后，MBT将发挥人工智能带来的最大价值，不只是效率提升，更是**测试工程师能力结构的重塑**。

## 岗位定义转变：从测试执行到SDT

传统测试工程师的核心能力是根据需求写用例，根据用例执行测试。在新范式中，测试工程师需要具备**规格驱动开发/测试（SDD-SDT, Spec-Driven Development / Spec-Driven Test）**的思维：

- 能够将模糊的业务描述抽象为**状态机模型**：识别状态、识别转换、识别触发条件
- 能够用YAML等**可执行规格**表达业务规则
- 能够判断“哪些业务适合用状态机建模”、“哪些状态应该合并/拆分”

这是一种**建模能力**，它介于产品经理的“需求表达”和工程师的“代码实现”之间。测试工程师对“边界条件”和“异常路径”的敏感度，使他们天生适合做这件事。

## 算法/数学知识：从黑盒使用者到白盒决策者

AI可以生成算法代码，但**判断算法是否适用**是人的职责。人类需要掌握理解图论、矩阵运算、概率论这些更为抽象的知识，能力关键不是会推导公式，而是知道“什么时候用什么工具”。这种判断力，是AI无法替代的。

## 方案决策：模型抽象程度与人力成本估算

AI提效带来的人员结构压缩要求方案决策者往下要了解业务细节，往上要评估测试资源的投入成本：

**模型抽象程度决策**：

- 建模太细：状态爆炸，路径组合不可控，维护成本高
- 建模太粗：遗漏关键细节，测试覆盖不足
- 判断标准：**如果模型能手动列出所有路径，就不需要MBT**；如果无法手工枚举，就需要建模

**人力成本估算**：

- 建模：YAML描述状态机（小时级）
- 工具：AI辅助生成脚本（天级）
- 用例：LLM生成 + 人工审查（小时级）
- 维护：模型变更时重新生成（分钟级）

**ROI判断**：

- 传统方式：单个状态机建模 + 路径设计 + 用例编写 + 维护 ≈ 9人天
- 新方式：YAML建模 + 脚本生成 + LLM用例 + 维护 ≈ 0.85人天
- 效率提升约**10倍**，覆盖度从约60%提升到约95%

## 能力结构的重塑

| 能力维度 | 传统测试工程师 | AI时代MBT工程师 |
|---------|--------------|----------------|
| 业务理解 | 深度理解流程 | 深度理解 + 抽象为状态机 |
| 建模能力 | 不要求 | 能用YAML/自然语言描述模型 |
| 编程能力 | 会写测试脚本 | 会用AI生成并审查框架代码 |
| 数学基础 | 不要求 | 懂图论、矩阵、概率论概念 |
| AI协作 | 不涉及 | 熟练用LLM做代码和用例生成 |
| 工具开发 | 用现成工具 | 快速自研场景化工具 |
| 方案决策 | 执行既定方案 | 判断抽象程度与ROI |

**AI把用例文本编写、用例脚本开发的工作接走了，留给人的是更靠近业务本质的建模、判断和决策**。测试工程师从“测试执行者”跃升为“测试建模者”和“质量架构师”。

# 结语：测试前移和SDD的一种落地范式

MBT从来不是技术问题，而是成本问题。

**传统MBT的困境**是：建模成本高 × 工具门槛高 × 迭代冲突 = 不可行。

**AI时代MBT的机遇**是：LLM降低建模门槛、LLM降低开发门槛、LLM降低维护门槛，三者叠加，成本下降10-100倍。

这意味着：小团队也能用MBT，敏捷迭代也能用MBT，每个测试工程师都能拥有“自己的MBT框架”。

技术基础没有变——状态机、图论、路径覆盖，这些数学工具几十年前就已成熟。真正变化的是**谁可以使用它**。过去需要专家团队、专门工具、周级建模周期，现在只需要一个测试工程师、一个YAML文件、一个Python脚本、一个LLM。门槛的降低，让MBT从“实验室技术”走向“工程实践”。

这个项目的价值，不在于发明了新技术，而在于把传统MBT从“少数专家的奢侈工具”变成了“测试工程师的日常武器”。在AI时代，**让好技术真正被用起来**，往往比发明新技术更有价值。

关键不是“用不用MBT”，而是“**你能不能快速为业务定制一个MBT框架**”。

而这，恰恰是AI时代测试开发工程师的核心竞争力。
