一个前端小白，靠 AI Agent 在本博客上做 UI 改版。全程我只会说“人话”，Agent 负责把“人话”翻译成 HTML/CSS/JS。
**唯一脑子灵机一动的时刻：“安装两个前端skill”**，让我从“一次次指令”变成了“有截图、有规范地协作”。

## 故事要从一个很“小”的需求说起

那天我看着自己博客的文章页，总觉得标题字太大。作为前端小白，我唯一的表达能力是：

> “文章页的标题字体有点大，改小一些。”

没有 CSS 类名，没有 `font-size`，甚至不确定“标题”指的是页首大标题还是正文里的 `##`。但这不重要——**把“感受”交给 Agent，把“技术”也交给 Agent**，就是我接下来一直在做的事。

第一轮，Agent 去翻了主题源码，回来告诉我：哦，这是 Hydejack 主题的“大标题特性”在作怪，宽屏下正文里的 `#` 会放大到 3–4rem，罪魁祸首找到了。然后它加了一段自定义样式，让我刷新看看。

我刷新，说：

> 还是大。——哦不对，我说的是正文里 Markdown 的 `#` 标题。

Agent：懂了，那是另一处。改。

几个来回之后，字号终于顺眼了。中途它还顺手帮我去掉了首页每篇文章卡片右下角的 “Continue reading …”——因为我随口说了一句“那个不需要，能删掉吗”。**你看，需求描述得越像“人话”，Agent 反而越不容易会错意。**

## 然后我膨胀了：要一个“悬浮目录”

文章长了，章节多了，我就想要一个“右上角能悬浮、点一下能跳章节”的目录。这需求放给真人前端，估计要开个会；放给 Agent，它直接开始写：

- 扫描正文的 `h1~h4`，生成锚点链接；
- 做滚动高亮；
- 处理“只在文章页出现”。

听起来很顺？并没有。接下来的对话是典型的“小白调 UI”现场：

- “一级标题没进目录！” → 它把 `h2/h3/h4` 的范围扩到 `h1`。
- “目录按钮怎么跑到首页去了？” → 它把判断条件改成“只有单篇文章页才显示”。
- “从首页点进文章，目录不出现，要刷新才行；反过来又不消失。” → 它发现这是主题的 **SPA（push-state）** 在作怪：页面切换不刷新，脚本没跟着更新，而且 `<main>` 的 class 在跳转后并不会变成文章页专属的 `layout-post`。

这一串，我一个名词都不认识，但 Agent 每次都能定位、修复，再让我验证。作为小白，我的工作只有两件事：**说感受**，和**点开看**。

到这一步，我隐约觉得“哪里不对劲”——效率确实可以，但每次都是“改→我刷新→我再反馈→再改”，闭环太长了。而且 Agent 虽然能截图，却没有一套稳定的“看完再改”的节奏。

## 关键转折：我学会了直接要 Skill

于是我停下来，换了个问法，不再描述某个具体 bug，而是问 Agent 一个“方法论”问题。**原话如下**：

> 我使用了 jekyll 开源模版，想在模版基础上二次开发，加上新的前端功能。
> 我是个前端小白，描述需求无法深入到技术层面，直接对话模型会比较费时费 token，
> 有可以推荐给我使用的 skill 吗。

AI 给我推荐了两个：

1. **`website-preview`** —— 本地渲染 Jekyll 站点、自动截图、验证 UI 改动；
2. **`jekyll-ui-web-designer`** —— 面向 Jekyll/静态站的 UI 设计与实现规范。

![安装skill后]({{ "/assets/img/blog/install-skill.png" | relative_url }})

装上之后，协作方式立刻不一样了：

- 以前：我手动刷新 → 肉眼看 → 打字反馈；
- 现在：Agent 改完样式 → 自动打开页面截图 → 把截图给我 → 我直接看效果再决定下一步。

“截图闭环”补上之后，后面几轮（目录只出现在文章页、一级标题进目录、SPA 往返正常）的确认都快了很多。**因为我和 Agent 终于有了同一个“视觉事实”——图片。**


## 测试：有 bug，直接让 Agent 改

Agent像一个手脚麻利的前端开发，免不了也会写出bug。在验收我的需求是发现几个问题：

> “目录按钮只能出现在文章详情页，不能出现在别的页面。”

Agent：明白了——首页的文章卡片其实也是 `article.post`，被我的兜底判断误伤了。改成按“正文里只有一个文章大标题”来识别详情页。你再看看。

> “从首页切换到详情页，没有目录按钮，要刷新才出现；从详情页回首页，按钮又不消失。”

这句话直接把 Agent 送进了 Hydejack 的 **SPA（push-state）** 深水区。它排查了半天，回报了我三个“惊喜”：

1. 页面跳转后 `<main>` 的 class 并不会变成文章页专属的 `layout-post`——所以它原来“按 class 找文章页”的逻辑在跳转后永远扑空；
2. 它自己写的脚本**漏了 `</script>` 闭合标签**，导致后面的 HTML 被整段吞掉（它原话：啊，是我漏了闭合标签，补上）；
3. 更隐蔽的是，脚本里的 `//` 行注释被主题的 HTML 压缩器吃掉换行后“污染”了后面的代码——**在别人的框架里写代码，连注释都有讲究**。

这三个问题如果是人类开发排查，估计都要定位大半天。
更惊喜的是 Agent 像一位资深前端专家，直接换了种解法：不去赌主题的自定义事件，而是直接**监听 `document.body` 的内容变化**，一旦正文被 SPA 替换就自动重建目录；再用一个“抑制开关”防止自己添加节点触发无限循环。修完之后它自己模拟了三轮“文章 → 普通页 → 文章”的内容切换，确认按钮该出现就出现、该消失就消失，才敢交给我验收。——还是个资深负责靠谱的前端专家。

## 复盘：小白用 AI Agent 的三条心得

1. **用“感受”描述需求，别装懂。** 我不知道 `h1`、`font-size`、`SPA`，但这不妨碍我表达“字太大”“按钮跑错页面了”“要刷新才出现”。Agent 会把感受翻译成定位与修复。
2. **主动要工具（Skill），而不是让模型硬扛。** 模型不是没有“截图能力”，而是把“截图/设计规范”这类能力**组织成可复用 Skill** 之后，每次调用都又快又稳，还省 token。那句“有可以推荐给我使用的 skill 吗”是整个过程的性价比之王。
3. **让 Agent 自己证明“改好了”。** 别只听它说“已完成”，要它截图 / 走一遍关键路径（首页→详情→首页）。视觉事实 > 口头保证。
